# DigitalTwin.ai

DigitalTwin.ai is a statistics-first digital twin for a mixed-model vehicle assembly line. It simulates vehicle movement, applies context-specific control limits, detects meaningful patterns rather than reacting to every noisy reading, forecasts growing constraints, and measures itself against injected ground truth.

## What it demonstrates

- 420 simulated vehicles across 40 stations in body construction, paint, and final assembly.
- Mixed sensor coverage: 70% richly instrumented and 30% manual checklist-only. Manual stations are explicitly labelled `manual outcome` or `adjacent-signal inference`; they never display invented sensor values.
- Point, trend, persistent, and cross-parameter anomaly rules using configurable z-score thresholds.
- Station and vehicle health/risk signals, queue/cycle/utilization tracking, emerging-bottleneck detection and downstream-starvation indication.
- A genuine deterministic backtest against separately logged injected ground truth, surfaced on the Leadership view.

## Illustrative assumptions

These are intentional prototype assumptions, not claims about a specific factory:

- The line contains approximately 40 stations and mixed vehicle variants.
- Approximately 70% of stations have continuous multi-parameter signals; the remaining 30% provide only pass/fail/rework outcomes.
- Sensor coverage could change only during four scheduled maintenance windows per year. This operational constraint is recorded but calendar scheduling is not simulated.

## Architecture

`config/line_config.json` -> synthetic generator -> contextual baseline (`station + parameter + variant`) -> anomaly and health engines -> bottleneck engine -> validation/backtest -> FastAPI -> React dashboard.

The configuration controls station groups, parameters, weights, coverage, thresholds, and injected scenarios. There are no real PLCs, OT systems, or factory data paths in this prototype.

## Run locally

Backend (from `backend/`):

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload
```

Frontend (from `frontend/`):

```bash
corepack pnpm install
corepack pnpm dev
```

Open the URL Vite prints, normally `http://localhost:5173`.

## Replay an anonymized historical CSV

The dashboard can replay either the built-in synthetic line or an uploaded historical extract. Start the app, choose **Line data CSV**, and click **Upload & replay**. Press **Start replay** to advance one vehicle every 0.85 seconds, or drag the replay slider to inspect a particular vehicle.

Use [line_data_template.csv](backend/sample_data/line_data_template.csv) as the column contract. Each continuous reading occupies one row; repeat the operation fields when a station has multiple parameter rows. Manual-only stations must leave `parameter` and `value` blank and provide `manual_outcome` (`pass`, `fail`, or `rework`). Station IDs and parameters must be configured in `backend/config/line_config.json`; unknown identifiers are rejected rather than guessed.

Optionally upload [ground_truth_template.csv](backend/sample_data/ground_truth_template.csv) as a second file. It supplies confirmed incidents for backtesting uploaded history. Uploaded data stays only in process memory and the integration remains read-only.
Without this second file, the dashboard marks validation metrics as unavailable rather than borrowing the synthetic demo's accuracy figures.

Run the validation independently:

```bash
cd backend
python run_backtest.py
```

It prints the metrics generated from the current deterministic simulation. The Leadership screen reads those same computed metrics - no performance claim is hardcoded.

### Default backtest result

With the included seed and configuration, the current run reports **60.0% incident precision**, **100.0% anomaly recall**, **2 false-positive station incidents**, a **10.0-vehicle mean detection lag**, and **100.0% bottleneck recall** over five injected scenarios. These values are regenerated by code; changing configuration or the simulation seed changes them.

## Dashboard views

- **Floor supervisor:** live line map, current station state, explicit sensor-gap status, and z-score control chart.
- **Plant manager:** cycle-time trend, station health bars, and deviation heatmap.
- **Leadership:** precision/recall/lag/bottleneck metrics, rollout sequence, and scalability note.

## Real-world integration

In a production pilot, this twin would attach as a **read-only listener** to existing PLC/OT historian, MES, and quality data. It would never write to PLCs or modify live control logic. Any physical sensor retrofit or coverage change would be planned inside the four yearly maintenance windows. Data mappings and context baselines would be validated line-by-line before a rollout.
